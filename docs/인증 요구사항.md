# 인증(Auth) 기능 요구사항 상세 명세

**범위**: 아이디+비밀번호 회원가입/로그인, OAuth 2.0 소셜 로그인, 세션 기반 인증, 역할 기반 접근 제어
**총 13건** (Auth-01 ~ Auth-13)

## 확정된 정책

| 항목 | 결정 |
|---|---|
| 로그인 식별자 | 아이디(loginId). 이메일은 식별자로 쓰지 않는다 |
| 이메일 인증 | 없음. 인증 메일을 발송하지 않는다 |
| 비밀번호·아이디 분실 | **복구 경로를 제공하지 않는다.** 분실 시 계정 영구 상실 |
| 아이디 재사용 | 탈퇴 계정의 아이디는 재사용 가능. unique 제약을 활성 회원에만 적용 |
| 소셜 전용 계정의 아이디 추가 | 제공하지 않음 |
| 세션 만료 | 절대 만료만 적용(유휴 만료 없음) |
| 비밀번호 해시 | Argon2id + 계정별 무작위 솔트 |

---

## 1. 요구사항 상세

### Auth-01 · 아이디 회원가입

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 회원가입 · 아이디 회원가입 |
| 설명 | 아이디와 비밀번호로 신규 계정을 생성한다 |
| 입력 | 아이디, 비밀번호, 비밀번호 확인, 닉네임, 약관 동의 항목. 이메일은 선택 입력 |
| 아이디 규칙 | 4~20자, 영문 소문자·숫자·언더스코어만 허용. 숫자로 시작 불가. 소문자로 정규화해 저장하고 대소문자를 구분하지 않고 중복 판정 |
| 비밀번호 규칙 | 8~64자, 영문·숫자·특수문자 중 2종 이상 조합. 아이디 문자열 포함 불가 |
| 닉네임 | 2~20자 |
| 이메일 | 선택 입력. 형식 검증만 하고 인증 메일을 발송하지 않는다. 용도는 알림 백업 채널 |
| 처리 | 비밀번호 + 솔트를 **Argon2id**로 해시 저장(솔트는 계정마다 무작위 생성, 파라미터와 함께 해시 문자열에 저장) → 회원 생성(상태 `ACTIVE`) → `BUYER` 역할 부여 → 약관 동의 이력 저장 → 세션 발급 |
| 해시 파라미터 | 메모리 19MiB 이상, 반복 2회 이상, 병렬도 1, 솔트 16바이트, 출력 32바이트 기준. 운영 서버에서 해시 1회가 0.5~1초를 넘지 않는 선에서 조정 |
| 결과 | 즉시 서비스 이용 가능. 별도 인증 단계가 없다 |
| 안내 | **비밀번호 분실 시 복구가 불가능함을 가입 화면에 명시**한다. 소셜 연동을 함께 권유해 로그인 수단을 이중화하도록 유도한다 |
| 예외 | 아이디 중복(Auth-03), 유효성 위반 시 필드별 오류 메시지 반환 |

### Auth-02 · 소셜 회원가입

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 회원가입 · 소셜 회원가입 |
| 설명 | 카카오·구글 계정으로 신규 가입한다 |
| 처리 | OAuth 2.0 Authorization Code 흐름 → `state` 파라미터로 CSRF 검증(5분 내 미사용 시 폐기) → 액세스 토큰 교환 → 사용자 정보 조회 → `(provider, providerUserId)`로 기존 연동 조회 → 없으면 신규 가입 |
| 저장 | `SocialCredential`(provider, providerUserId, 연동 시각) 생성. `LocalCredential`은 만들지 않는다 |
| 아이디 | 소셜 가입 회원은 아이디를 갖지 않으며, 이후에도 추가할 수 없다 |
| 이메일 | 제공자가 주면 저장하고, 주지 않으면 비워둔다. 추가 입력을 요구하지 않는다 |
| 닉네임 | 제공자 닉네임을 초기값으로 사용한다 |
| 상태 | `ACTIVE`로 시작 |
| 예외 | 사용자 취소·토큰 오류는 사유를 구분해 안내 |

### Auth-03 · 아이디 중복 검사

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 회원가입 · 아이디 중복 검사 |
| 설명 | 사용 가능한 아이디인지 확인한다 |
| 처리 | 실시간(입력 중) 확인과 가입 요청 시 최종 확인을 모두 수행한다 |
| 정규화 | 소문자로 변환한 값을 기준으로 비교한다 |
| DB 제약 | **활성 회원에 한정한 부분 unique 인덱스**를 건다. 탈퇴 회원의 아이디는 중복 판정에서 제외된다 |
| 인덱스 예시 | `CREATE UNIQUE INDEX uk_member_login_id ON member (login_id) WHERE status <> 'WITHDRAWN';` (PostgreSQL 부분 인덱스) |
| 응답 | 사용 가능 / 이미 사용 중 두 가지로만 분기한다 |
| 비고 | 탈퇴 직후 타인이 같은 아이디를 가져갈 수 있다. 이전 회원으로 오인될 소지가 있으므로, 문제가 되면 탈퇴 후 일정 기간 유예를 추가한다 |

### Auth-04 · 아이디 로그인

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 로그인/로그아웃 · 아이디 로그인 |
| 설명 | 가입한 아이디와 비밀번호로 인증한다 |
| 처리 | 아이디를 소문자로 정규화해 조회 → 비밀번호 + 솔트 해시 대조 → 성공 시 **기존 세션 ID 폐기 후 새 세션 발급**(세션 고정 공격 방지) → 역할·상태를 세션에 적재 → `SID` 쿠키 발급 |
| 조회 조건 | 상태가 `WITHDRAWN`인 회원은 조회 대상에서 제외한다 |
| 쿠키 | `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 128비트 이상 난수 |
| 유지 옵션 | 유휴(sliding) 만료를 두지 않고 **절대 만료만** 적용한다. `로그인 유지` 미선택 시 24시간, 선택 시 14일. 세션 생성 시점에 TTL을 한 번 설정하고 이후 갱신하지 않는다 |
| 응답 | 실패 시 아이디·비밀번호 중 무엇이 틀렸는지 구분하지 않고 동일 메시지 반환 |

### Auth-05 · 소셜 로그인

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 로그인/로그아웃 · 소셜 로그인 |
| 설명 | 이미 연동된 소셜 계정으로 인증한다 |
| 처리 | Auth-02와 동일한 OAuth 흐름 → `(provider, providerUserId)` 일치 회원 조회 → 세션 발급 |
| 세션 | 아이디 로그인과 동일한 세션 정책을 적용한다. 제공자 액세스 토큰은 세션에 저장하지 않는다 |
| 예외 | 연동 정보 없음 → 가입 흐름으로 분기. 제공자 장애 시 아이디 로그인으로 안내 |

### Auth-06 · 로그아웃

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 로그인/로그아웃 · 로그아웃 |
| 설명 | 현재 세션을 종료한다 |
| 처리 | 세션 스토어에서 해당 세션 삭제 → 쿠키 만료 → 회원별 세션 역인덱스에서 제거 |
| 주의 | 소셜 로그인 회원의 로그아웃은 서비스 세션만 종료하며, 제공자 세션은 유지된다(연결 끊기와 구분) |

### Auth-07 · 실패 제어

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 로그인/로그아웃 · 실패 제어 |
| 설명 | 연속 로그인 실패를 제한해 무차별 대입을 차단한다 |
| 규칙 | 계정 기준 연속 실패 5회 → 10분간 로그인 차단. 성공 시 카운터 초기화 |
| 저장 | 실패 카운터는 Redis에 TTL과 함께 저장 |
| 중요도 | **분실 복구 경로가 없으므로 계정 탈취가 곧 영구 상실**이 된다. 본 요구사항이 사실상 유일한 대입 공격 방어선이다 |
| 제외 | IP 기준 제한과 차단 통지는 MVP 범위에서 제외 |

### Auth-08 · 비밀번호 변경

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 계정 관리 · 비밀번호 |
| 설명 | 로그인 상태에서 비밀번호를 변경한다 |
| 대상 | `LocalCredential` 보유 회원만 해당. 소셜 전용 회원은 비밀번호가 없으므로 메뉴 자체를 노출하지 않는다 |
| 입력 | 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인 |
| 검증 | 현재 비밀번호 일치, 신규 비밀번호 규칙 충족, 직전 비밀번호와 동일 불가 |
| 처리 | 새 솔트를 생성해 비밀번호 + 솔트 해시 갱신 → **현재 세션만 유지하고 나머지 세션 전부 무효화** |

### Auth-09 · 소셜 계정 연결 및 해제

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 계정 관리 · 계정 연동 |
| 설명 | 로그인 상태에서 소셜 제공자를 추가 연동하거나 해제한다 |
| 연동 | OAuth 인증 후 `SocialCredential` 추가. 이미 다른 회원에 연동된 소셜 계정이면 거부 |
| 판정 기준 | `(provider, providerUserId)`만으로 판정한다. 이메일 일치를 근거로 한 계정 병합이나 본인 확인 절차를 두지 않는다 |
| 해제 | 로그인 수단이 최소 1개 남는 경우에만 허용. 마지막 수단 해제는 차단 |
| 권장 | 아이디 회원에게 소셜 연동을 권유한다. 분실 복구 경로가 없는 구조에서 **로그인 수단 이중화가 사실상 유일한 보험**이다 |
| 제약 | 소셜 전용 회원은 소셜을 1개만 보유한 경우 해제할 수 없다(아이디 추가 경로가 없으므로) |

### Auth-10 · 약관 동의 및 이력 관리

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 계정 관리 · 약관 및 동의 관리 |
| 설명 | 가입 시 약관 동의를 받고 항목별 이력을 보관한다 |
| 필수 항목 | 서비스 이용약관, 개인정보 처리방침, 만 14세 이상 확인 |
| 선택 항목 | 마케팅 정보 수신. 채널(앱푸시·이메일)별로 분리해 받는다 |
| 저장 | 회원 ID, 약관 종류, **약관 버전**, 동의 여부, 동의 시각을 이력으로 저장한다. 갱신이 아니라 누적 기록 |
| 소셜 가입 | 소셜 회원도 동일하게 동의를 받는다. 제공자 인증 후 추가 입력 단계에서 처리 |
| 철회 | 선택 항목은 언제든 철회 가능하며 철회도 이력으로 남긴다 |
| 약관 개정 | 개정 시 새 버전을 등록하고, 이전 버전에 동의한 회원을 조회할 수 있어야 한다 |
| 법적 근거 | 전자상거래법·개인정보보호법상 동의 시점과 내용을 입증할 수 있어야 한다 |

### Auth-11 · 회원 탈퇴

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 계정 관리 · 탈퇴 |
| 설명 | 회원이 계정을 삭제한다 |
| 사전 확인 | `LocalCredential` 보유 회원은 비밀번호 재확인, 소셜 전용 회원은 연동된 제공자로 재인증 |
| 차단 조건 | 결제 대기·결제 완료 미배송 주문 보유, 구매 신청 후 마감 대기 중, 셀러로서 낙찰 후 미완료 공구 보유 |
| 처리 | 전 세션 삭제 → 상태 `WITHDRAWN` → 개인정보 즉시 파기 → 법정 보존 대상만 분리 보관 |
| 아이디 | 부분 unique 인덱스 범위에서 벗어나므로 **탈퇴 즉시 다른 회원이 동일 아이디를 사용할 수 있다** |
| 재가입 | 신규 가입으로만 가능하며 이전 계정 데이터는 복구되지 않는다 |
| 예외 | 차단 시 사유와 해당 건 목록을 함께 안내 |

### Auth-12 · 판매자 역할 부여

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 권한 · 역할 부여 |
| 설명 | 구매자 회원이 판매자 정보를 등록해 `SELLER` 역할을 획득한다. `member`와 `seller`는 1:1로 연결된다 |
| 진입 조건 | 상태 `ACTIVE` |
| 입력 (필수) | 상호명, 사업자등록번호, 통신판매업 신고번호, 대표자명, 연락처, 정산 계좌(은행명·계좌번호·예금주명), 취급 카테고리 1개 이상 |
| 사업자등록번호 검증 | **형식 검증만 수행한다.** 하이픈 제거 후 숫자 10자리인지 확인하고, 국세청 체크섬(가중치 `1,3,7,1,3,7,1,3,5`, 9번째 자리 몫 가산 후 10에서 나머지를 뺀 값이 마지막 자리와 일치)으로 유효성을 판정한다. 실존·휴폐업 확인은 하지 않는다 |
| 통신판매업 신고번호 검증 | 표기 방식이 지자체별로 달라 엄격한 패턴을 강제하지 않는다. 공백 제거 후 길이 범위와 허용 문자만 확인한다 |
| 저장 형식 | 사업자등록번호와 계좌번호는 하이픈을 제거해 저장한다 |
| 중복 검증 | 동일 사업자등록번호로 이미 등록된 판매자가 있으면 거부한다 |
| 처리 | 형식 검증 통과 시 `seller` 레코드 생성 → MVP에서는 심사 없이 즉시 `APPROVED` 전이 및 `approved_at` 기록 → `SELLER` 역할 부여 |
| 판매자 상태 | `PENDING`(승인대기) → `APPROVED`(승인됨) → `BLOCKED`(정지됨) / `WITHDRAWN`(탈퇴). 컬럼 기본값은 `PENDING`이며, 심사 도입 시 자동 전이만 제거하면 되도록 설계한다 |
| 세션 반영 | **세션을 무효화하지 않고 권한 정보만 갱신**한다. 재로그인 없이 즉시 응찰 가능해야 한다 |
| 응찰 가능 조건 | `seller_status = APPROVED` 이며 `deleted_at`이 `NULL`인 경우에만 상품 등록·응찰을 허용한다 |
| 수정 범위 | 등록 후 **상호명·사업자등록번호·통신판매업 신고번호·대표자명은 변경할 수 없다.** 연락처와 정산 계좌만 수정 가능 |
| 민감정보 | 계좌번호와 사업자등록번호는 암호화 저장하고, 목록 화면에서는 마스킹한다 |
| 삭제 | 물리 삭제 없이 `deleted_at`으로 소프트 삭제한다 |
| 미반영 항목 | 취급 카테고리는 다중값이므로 `seller_category` 매핑 테이블이 별도로 필요하다 |

### Auth-13 · 역할별 접근 제어

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 권한 · 접근 제어 |
| 설명 | 요청자의 역할과 상태에 따라 API 접근을 통제한다 |
| 응답 규칙 | 미인증 401, 권한 부족 403으로 구분 |
| 역할 요구 | 수요 등록·구매 신청·결제 → `BUYER` + `ACTIVE` / 상품 등록·응찰·주문 관리 → `SELLER` + `APPROVED` |
| 소유권 검증 | 역할 검사와 별개로 리소스 소유자 일치를 확인한다. 타인의 수요·응찰·주문·배송지 접근 차단 |
| 데이터 격리 | 수요 현황은 등록자 본인만 열람. 셀러는 카테고리별 전체 수요를 조회하되 참여자 식별 정보는 비노출 |
| 컨텍스트 | 구매자/셀러 모드가 요청 대상과 불일치하면 전환을 유도 |

## 2. 분실 복구 미제공에 따른 보완 조치

복구 경로가 없다는 결정은 **계정 탈취와 비밀번호 분실이 곧 영구 상실**을 뜻한다. 아래는 코드 변경 없이 또는 최소 비용으로 위험을 낮추는 조치다.

| 조치 | 내용 | 반영 위치 |
|---|---|---|
| 가입 시 고지 | "비밀번호를 잊으면 계정을 복구할 수 없습니다"를 가입 화면에 명시 | Auth-01 |
| 소셜 연동 권유 | 가입 완료 후 소셜 연동을 권유해 로그인 수단을 이중화 | Auth-09 |
| 실패 제어 유지 | 대입 공격 방어선이 Auth-07 하나뿐이므로 완화하지 않는다 | Auth-07 |
| 세션 무효화 유지 | 비밀번호 변경 시 다른 세션 정리 | Auth-08 |
| 탈퇴 차단 조건 유지 | 진행 중 거래가 있으면 탈퇴 차단 | Auth-11 |

**나중에 추가할 때의 진입점** — 이메일 기반 재설정을 도입하려면 Auth-01의 이메일을 필수로 바꾸고 재설정 요구사항 1건을 추가하면 된다. 스키마 변경은 이메일 컬럼의 `NOT NULL` 전환뿐이다.

**유지한 보안 항목**

- 비밀번호 해시 저장(Argon2id + 솔트)
- 로그인 시 세션 ID 재발급(세션 고정 공격 방지)
- 로그인 실패 5회 차단
- 비밀번호 변경 시 다른 세션 무효화
- 마지막 로그인 수단 해제 차단
- 쿠키 `HttpOnly` / `Secure` / `SameSite`
- OAuth `state` 검증
- 소유권 검증 및 수요 데이터 격리
- 계좌번호·사업자등록번호 암호화 저장
