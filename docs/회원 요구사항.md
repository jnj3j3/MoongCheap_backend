# 회원(User) 기능 요구사항 상세 명세

**범위**: 프로필, 배송지, 판매자 등록·관심 카테고리, 주문용 회원 정보 제공
**전제**: 로그인 식별자는 아이디(loginId), 소셜 로그인은 OAuth 2.0. 인증 관련은 별도 문서(인증 요구사항 상세) 참조

---

## 1. 기존 요구사항 상세

### User-01 · 프로필 조회

| 항목 | 내용 |
|---|---|
| 설명 | 본인 프로필 정보를 조회한다 |
| 대상 | 소비자, 판매자 |
| 응답 항목 | 아이디, 닉네임, 프로필 이미지, 연락처, 이메일, 가입일, 판매자 여부, 연동된 소셜 제공자 목록 |
| 마스킹 | 연락처는 중간 자리를 마스킹해 반환하고, 수정 화면 진입 시에만 전체 값을 조회한다 |
| 판매자 | `SELLER` 역할 보유 시 판매자 정보 요약(상호명, 승인 상태, 관심 카테고리)을 함께 반환한다 |
| 제외 | 비밀번호 해시, 소셜 액세스 토큰, 계좌번호 전체 값은 어떤 경우에도 반환하지 않는다 |
| 권한 | 본인만 조회 가능. 타인 프로필 조회 API는 제공하지 않는다 |

### User-02 · 프로필 수정

| 항목 | 내용 |
|---|---|
| 설명 | 닉네임, 연락처 등 프로필을 수정한다 |
| 대상 | 소비자, 판매자 |
| 수정 가능 | 닉네임, 프로필 이미지, 연락처, 이메일 |
| 수정 불가 | **아이디는 변경할 수 없다.** 로그인 식별자이자 중복 검사 기준이므로 변경 시 세션·이력 정합성 문제가 발생한다 |
| 검증 | 닉네임 2~20자 및 중복 검사(User-03), 연락처 숫자만 허용(하이픈 제거 후 저장), 이메일 형식 검증 |
| 이메일 | 검증 메일을 발송하지 않는다. 다만 비밀번호 분실 시 복구 수단이므로 변경 시 안내 문구를 노출한다 |
| 프로필 이미지 | 5MB 이하, jpg·png·webp 허용. 업로드 시 서버에서 확장자·MIME 타입을 함께 검증하고 리사이즈해 저장한다 |
| 부분 수정 | 변경된 필드만 전달받아 처리한다(PATCH 방식) |
| 반영 범위 | 닉네임 변경은 이후 노출부터 적용된다. 이미 생성된 주문·응찰의 스냅샷에는 소급하지 않는다 |

### User-03 · 닉네임 중복 정책

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 프로필 · 닉네임 |
| 설명 | 닉네임은 서비스 내에서 유일해야 한다 |
| 규칙 | **중복 불가.** DB unique 제약으로 강제한다 |
| 정규화 | 앞뒤 공백을 제거하고 연속 공백을 하나로 합친 뒤 비교한다. 대소문자 구분 여부를 정해야 하며, 구분하지 않는 쪽을 권장한다 |
| 탈퇴 회원 | 아이디와 동일하게 **활성 회원에 한정한 부분 unique 인덱스**를 적용해 탈퇴 후 재사용을 허용한다 |
| 인덱스 예시 | `CREATE UNIQUE INDEX uk_member_nickname ON member (nickname) WHERE deleted_at IS NULL;` |
| 중복 검사 | 가입·수정 화면에서 실시간 확인을 제공하고, 저장 시 최종 확인한다 |
| 소셜 가입 | 제공자 닉네임이 이미 사용 중이면 자동으로 접미사(숫자)를 붙여 생성하고 사용자에게 알린다. 가입 흐름이 중단되지 않게 한다 |
| 예외 | 유니크 제약 위반은 경합 시에도 발생하므로, DB 예외를 잡아 사용자 친화적 메시지로 변환한다 |

### User-04 · 배송지 등록

| 항목 | 내용 |
|---|---|
| 설명 | 배송지를 등록한다 |
| 대상 | 소비자 |
| 입력 | 배송지 별칭, 수령인명, 연락처, 우편번호, 기본 주소, 상세 주소, 배송 요청사항(선택) |
| 주소 검색 | 우편번호 검색 API를 연동한다. 기본 주소는 직접 입력하지 못하게 하고 검색 결과만 저장한다 |
| 검증 | 우편번호 5자리, 수령인명 2~20자, 연락처 형식. 상세 주소는 50자 이내 |
| 최초 등록 | 첫 배송지는 자동으로 기본 배송지가 된다 |
| 진입 경로 | 마이페이지 또는 **구매 신청 단계에서 배송지가 없을 때 등록을 요구**한다 |
| 저장 | 상세 주소와 연락처는 개인정보이므로 암호화 저장 대상 여부를 검토한다 |

### User-05 · 배송지 목록 관리

| 항목 | 내용 |
|---|---|
| 설명 | 배송지를 추가·수정·삭제한다 |
| 대상 | 소비자 |
| 개수 제한 | 최대 5개. 초과 시 기존 배송지 삭제를 안내한다 |
| 목록 정렬 | 기본 배송지를 최상단에 두고, 나머지는 최근 등록순으로 정렬한다 |
| 수정 | 등록과 동일한 검증을 적용한다 |
| 삭제 | 소프트 삭제 없이 물리 삭제한다. **진행 중 주문에는 영향을 주지 않는다**(주문 생성 시 배송지 값을 복사 저장하므로) |
| 기본 배송지 삭제 | 자동 승격을 하지 않는다. 기본 배송지가 없는 상태가 되며, 구매 신청 화면에서 배송지를 선택하도록 한다 |
| 마지막 배송지 삭제 | 별도 차단 없이 허용한다. 구매 신청 시점에 배송지가 없으면 등록을 요구한다 |
| 권한 | 본인 소유 배송지만 조회·수정·삭제 가능 |

### User-06 · 기본 배송지 지정

| 항목 | 내용 |
|---|---|
| 설명 | 기본 배송지를 지정한다 |
| 대상 | 소비자 |
| 저장 구조 | **`shipping_address.is_default` 플래그**로 관리한다. `member`가 배송지를 참조하지 않으므로 두 테이블 간 순환 참조가 생기지 않고, 배송지 목록 조회 한 번으로 기본 여부까지 알 수 있다 |
| 유일성 강제 | 부분 unique 인덱스로 DB가 보장한다. `CREATE UNIQUE INDEX ... ON shipping_address (member_id) WHERE is_default = TRUE;` |
| 규칙 | 회원당 최대 1개 |
| 변경 순서 | 트랜잭션 안에서 **기존 기본 배송지를 먼저 해제한 뒤** 새 배송지를 지정한다. 순서가 반대면 유니크 위반이 발생한다 |
| 최초 등록 | 첫 배송지 등록 시 자동으로 기본 배송지가 된다 |
| 삭제 연동 | 기본 배송지를 삭제하면 그대로 사라진다. 다른 배송지를 자동 승격시키지 않는다 |
| 활용 | 구매 신청 화면에서 기본 배송지를 초기 선택값으로 제시한다. 기본 배송지가 없으면 선택을 요구한다 |

### User-07 · 판매자 등록 신청

| 항목 | 내용 |
|---|---|
| 설명 | 사업자 정보를 등록해 판매자 등록을 신청한다 |
| 대상 | 소비자 |
| 정본 | **인증 문서의 Auth-12(판매자 역할 부여)와 동일한 기능이다.** 입력 항목, 사업자등록번호·통신판매업 신고번호 검증 방식, 승인 처리, 판매자 상태 전이, 세션 반영, 수정 가능 범위, 민감정보 처리는 모두 Auth-12에 정의되어 있다. 내용이 갈라지지 않도록 본 문서에 다시 적지 않는다 |
| 입력 (필수 추가) | 관심 카테고리 1개 이상. 미설정 시 수요를 전혀 조회할 수 없으므로 등록 단계에서 반드시 받는다(User-08) |
| 진입 경로 | 마이페이지 내 판매자 등록 메뉴 |

### User-08 · 관심 카테고리 설정

| 항목 | 내용 |
|---|---|
| 설명 | 판매자가 수요를 조회할 카테고리를 지정한다. **지정한 카테고리에 속한 수요만 조회할 수 있다** |
| 대상 | 판매자 |
| 성격 | 수요 조회 범위를 정하는 설정이다. 관심 카테고리 밖의 수요는 목록에 노출되지 않는다 |
| 저장 구조 | 다중값이므로 `seller_interest_category(seller_id, category_id)` 매핑 테이블이 필요하다 |
| 개수 | **최소 1개 필수**, 최대 10개. 0개가 되면 아무 수요도 볼 수 없으므로 허용하지 않는다 |
| 시점 | 판매자 등록 시 필수로 입력하고, 이후 언제든 추가·삭제할 수 있다 |
| 마지막 1개 | 삭제를 차단한다. 변경이 필요하면 추가 후 삭제하거나 교체로 처리한다 |
| 활용 1 | 수요 목록 조회 시 필터로 적용한다 |
| 알림 없음 | 관심 카테고리에 신규 수요가 등록되어도 **알림을 발송하지 않는다.** 판매자가 직접 목록을 확인하는 방식이다 |
| 반영 시점 | 변경은 이후 조회·발송분부터 적용된다. 이미 발송된 알림에는 소급하지 않는다 |
| 진행 중 건 | 카테고리를 삭제해도 이미 등록한 상품과 진행 중인 응찰은 목록·상세에서 계속 조회할 수 있다. 내 응찰 조회는 수요 조회와 별도 경로로 처리한다 |

### User-09 · 주문용 회원 정보 제공

| 항목 | 내용 |
|---|---|
| 설명 | 주문 생성 시 회원 도메인이 배송지와 연락처 값을 주문 도메인에 넘긴다 |
| 대상 | 시스템(애플리케이션 내부) |
| 구조 | **단일 서버 내 도메인 간 호출이다.** 별도 API나 네트워크 통신이 아니라 회원 도메인의 서비스 메서드를 주문 도메인에서 호출하는 형태 |
| 제공 항목 | 선택된 배송지(수령인명, 연락처, 우편번호, 주소, 요청사항), 주문자 연락처, 닉네임 |
| 호출 시점 | 구매 신청 생성 시 |
| **스냅샷 원칙** | 주문 엔티티는 배송지를 **FK로 참조하지 않고 값을 복사해 컬럼으로 보관**한다. FK로 두면 이후 배송지 수정·삭제 시 과거 주문의 배송 정보가 함께 바뀌어 배송 사고와 분쟁의 원인이 된다 |
| 정합성 | 값을 넘기기 전에 배송지 소유자가 요청자 본인인지 검증한다 |
| 제외 | 아이디, 이메일, 판매자 정산 정보는 넘기지 않는다 |
| 의존 방향 | 주문 → 회원 단방향으로 유지한다. 회원 도메인이 주문 도메인을 참조하지 않도록 해야 순환 의존이 생기지 않는다 |
| 반환 형태 | 엔티티를 그대로 넘기지 않고 필요한 값만 담은 DTO로 전달한다. 주문 쪽에서 회원 엔티티를 직접 수정할 수 없게 하기 위함 |

## 2. 추가 요구사항

### User-10 · 정산 계좌 관리

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 판매자 · 정산 계좌 |
| 설명 | 판매자가 정산받을 계좌를 조회·변경한다 |
| 대상 | 판매자 |
| 조회 | 은행명과 예금주명은 그대로, 계좌번호는 뒤 4자리만 노출하고 나머지는 마스킹한다 |
| 변경 입력 | 은행명, 계좌번호, 예금주명 |
| **본인 확인** | 변경 시 **비밀번호 재확인을 요구한다.** 계좌 변경은 정산금 수취인이 바뀌는 작업이라 세션 탈취만으로 실행되면 금전 피해로 직결된다 |
| 소셜 전용 회원 | 비밀번호가 없으므로 연동된 소셜 제공자로 재인증한다 |
| 검증 | 은행 코드 유효성, 계좌번호 숫자 형식. **실명 확인(예금주 조회) API는 연동하지 않는다.** 오입력 시 정산 실패로 드러나며, 운영자가 확인해 재입력을 요청한다 |
| 저장 | 하이픈을 제거해 정규화하고 암호화 저장한다 |
| 변경 제한 | 정산 처리 중인 건이 있으면 변경을 차단한다. 정산 대상 확정 시점에 계좌를 고정한다 |
| 이력 | 변경 이력(변경 시각, 이전 계좌 마스킹 값)을 보관한다. 정산 분쟁 시 근거가 된다 |
| 예금주명 | 사업자 판매자는 상호명과 예금주명이 다를 수 있으므로 일치 검증을 하지 않는다 |

### User-11 · 알림 수신 설정 관리

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 알림 · 수신 설정 |
| 설명 | 채널별·유형별 알림 수신 여부를 설정한다 |
| 대상 | 소비자, 판매자 |
| 채널 | **SSE 기반 인앱 알림 단일 채널.** 앱 푸시와 이메일은 도입하지 않는다 |
| 유형 (구매자) | 수요 등록·병합, 모집 현황, 낙찰 결과, 결제 예정·완료, 결제 실패, 배송, 무산 |
| 유형 (판매자) | 응찰 경쟁 현황, 낙찰·미낙찰, 주문 발생, 재고 소진 |
| **해제 불가 항목** | 낙찰 결과, 결제 예정·실패, 무산, 배송은 거래 필수 알림이므로 해제할 수 없다. 화면에서 비활성 상태로 표시하고 사유를 안내한다 |
| 알림함 적재 | 수신 설정과 무관하게 알림함에는 항상 적재한다. 설정은 **SSE 실시간 푸시 여부만** 제어한다 |
| 미접속 시 | SSE는 접속 중인 클라이언트에만 도달한다. 미접속 상태에서 발생한 알림은 재접속 시 알림함에서 확인하며, 미읽음 뱃지로 노출한다 |
| 저장 구조 | 채널 차원이 없으므로 `member_notification_setting(member_id, type, enabled)` 형태면 충분하다 |
| 기본값 | 신규 회원은 전 항목 수신 상태로 시작한다 |
| 미설정 처리 | 레코드가 없으면 기본값을 따른다. 가입 시 전 유형의 레코드를 미리 생성하지 않는다 |
| 확장 고려 | 이후 푸시·이메일을 추가하면 채널 차원이 필요해진다. 유형과 채널을 분리 가능한 형태로 설계해두면 마이그레이션 부담이 줄어든다 |

### User-12 · 판매자 공개 정보 노출

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 판매자 · 공개 프로필 |
| 설명 | 구매자가 상품 상세에서 확인하는 판매자 정보를 제공한다 |
| 대상 | 소비자(조회), 판매자(대상) |
| 법적 배경 | 전자상거래법상 통신판매업자는 상호, 대표자 성명, 영업소 소재지, 연락처, 사업자등록번호, 통신판매업 신고번호를 표시할 의무가 있다. **표시 범위와 방식은 법무 검토를 거쳐 확정한다** |
| 공개 항목 | 상호명, 대표자명, 사업자등록번호, 통신판매업 신고번호, 사업장 연락처 |
| 비공개 항목 | 정산 계좌, `member`의 개인 연락처, 이메일, 아이디, 회원 닉네임과의 연결 관계 |
| 노출 위치 | 상품 상세 하단의 판매자 정보 영역. 별도 페이지로 분리해도 무방하다 |
| 연락처 | `seller.phone_number`(사업장 연락처)를 공개한다. 회원 개인 연락처는 `member` 테이블에 별도로 저장되며 공개 대상이 아니다 |
| 상태 반영 | `BLOCKED`·`WITHDRAWN` 판매자의 상품은 노출되지 않으므로 공개 정보도 함께 숨긴다 |
| 캐싱 | 변경 빈도가 낮으므로 캐싱해도 되지만, 판매자 정지 시 즉시 반영되어야 한다 |

### User-13 · 정산용 판매자 정보 제공

| 항목 | 내용 |
|---|---|
| 대분류 · 중분류 | 정보 제공 · 판매자 정보 |
| 설명 | 정산 처리 시 판매자의 계좌 정보를 정산 도메인에 전달한다 |
| 대상 | 시스템(애플리케이션 내부) |
| 제공 항목 | 은행명, 계좌번호(복호화된 값), 예금주명, 사업자등록번호, 상호명 |
| 호출 시점 | 정산 대상 확정 및 지급 실행 시 |
| **복호화 지점 단일화** | 계좌번호 복호화는 회원 도메인 내부에서만 수행한다. 암호문을 다른 도메인에 넘기지 않으며, 복호화 키가 여러 곳에 흩어지지 않게 한다 |
| 호출 제한 | 정산 도메인의 지정된 서비스에서만 호출할 수 있도록 접근 범위를 제한한다. 컨트롤러에서 직접 호출하지 않는다 |
| 로깅 금지 | 반환값이 로그·에러 메시지·모니터링 지표에 남지 않도록 한다 |
| 스냅샷 | 정산 실행 시점의 계좌 정보를 정산 레코드에 복사 저장한다. 이후 계좌가 바뀌어도 과거 정산 내역의 지급처가 변하지 않아야 한다 |
| 검증 | 판매자 상태가 `APPROVED`이고 `deleted_at`이 `NULL`인지 확인한다 |

## 4. 미결 사항

1. **연락처·상세 주소 암호화 범위** — 개인정보보호법상 안전조치 의무 대상 판단이 필요하다. 암호화 시 컬럼 길이와 검색 방식(부분 일치 조회 불가)에 영향
2. **탈퇴 시 배송지 처리** — 즉시 파기가 원칙이나, 배송 중인 주문의 배송지 스냅샷은 주문 도메인에 남는다. 파기 범위를 명확히 해야 한다
3. **닉네임 대소문자 구분 여부** — 구분하지 않는 쪽을 권장하나 확정 필요(User-13)
